# Тестовые релизы ChessMentor через GitHub Releases

Релиз запускается **пушем тега**, а не пушем ветки. Для тега выполняется тот же Android CI (JVM, Room, Lint, сборка APK и проверка ELF). Только после успеха обоих заданий workflow скачивает артефакт **этого запуска**, выравнивает и подписывает Release APK без повторной сборки. Итог — черновик с APK, файлом `.sha256` и автоматически собранным списком изменений. Тег `-rc.N` помечается как prerelease. Google Play в этом процессе не задействован.

## Настройка один раз (владелец репозитория)

1. Защитите `master` и теги `v*` через rulesets: создание релизных тегов — только ответственным за выпуск, изменение и удаление запрещены. Workflow проверяет, что коммит входит в историю `master`; это не заменяет контроль права создавать теги.
2. До первого запуска создайте **Settings → Environments → `android-release`**. Разрешите развёртывания только для тегов `v*` (не веток), включите required reviewers и запрет самоодобрения, если это доступно. У обычного CI нет доступа к этому environment.
3. Используйте постоянный закрытый ключ подписи приложения. Если обновляете ранее распространявшийся APK, нужен **тот же ключ**. Храните резервную копию keystore и паролей отдельно. Не кладите их в репозиторий, логи или сообщения. Добавьте именно **environment secrets**:

   | Secret | Значение |
   |---|---|
   | `ANDROID_KEYSTORE_BASE64` | Содержимое JKS в base64 (одна строка). Base64 не шифрует файл. |
   | `ANDROID_KEYSTORE_PASSWORD` | Пароль хранилища |
   | `ANDROID_KEY_ALIAS` | Alias ключа |
   | `ANDROID_KEY_PASSWORD` | Пароль ключа |

   Для загрузки файла с машины владельца без вывода ключа на экран (GNU/Linux): `base64 -w0 release.jks | gh secret set ANDROID_KEYSTORE_BASE64 --env android-release`. Для остальных секретов используйте скрытый ввод `gh secret set ИМЯ --env android-release`.

## Выпуск

1. После слияния workflow в `master` выберите проверенный коммит. Возьмите версию **выше всех ранее распространённых**. Допустимы `vX.Y.Z` и `vX.Y.Z-rc.N`, где X, Y, Z от 0 до 99 без ведущих нулей, версия не `0.0.0`, N от 1 до 98. Например, для `v1.1.0-rc.1` приложение получит `versionName=1.1.0-rc.1`, `versionCode=1010001`; стабильный `v1.1.0` получит `1010099`. Повторный запуск того же тега не меняет код версии.
2. Создайте и отправьте **только нужный тег** (пример: `git tag -a v1.1.0-rc.1 <commit> -m 'ChessMentor RC 1'`, затем `git push origin refs/tags/v1.1.0-rc.1`). Дождитесь CI и одобрите задание `draft`.
3. В **Releases → Drafts** проверьте заметки и APK до ручного **Publish release**. Если подпись/проверки не прошли, изучите лог задания, исправьте настройку и перезапустите; не переносите тег на другой коммит. При изменениях кода нужен новый тег. Если загрузка вложений прервалась, проверьте черновик перед повтором: неполный выпуск не публикуйте.
4. Тестировщик скачивает APK и `.sha256` из опубликованного выпуска. В каталоге загрузок: `sha256sum -c ChessMentor-v1.1.0-rc.1.apk.sha256`. Для проверки обновления установите поверх предыдущего подписанного выпуска (`adb install -r <apk>`) и проверьте прогресс. Debug-сборка с другим сертификатом не обновится поверх release и наоборот; перед удалением приложения экспортируйте прогресс.
